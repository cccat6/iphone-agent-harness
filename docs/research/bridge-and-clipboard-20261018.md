# ESP32 桥状态、固件与剪贴板

本轮实现用户要求的三项变更。

## C3 固件

仅访问授权串口 `1101`，确认目标为原 C3 后写入已审查的新候选；四段写入校验通过，保留 NVS，重启后 Wi-Fi 恢复。四平台发布产物全部更新到同一源码，C3 发布文件与实际刷写文件逐字节一致。

新固件将蓝牙名设为 **iPhone Agent Bridge**，移除了新手机配对的隐藏两分钟网页窗口，并修复旧离线绑定占用名额的问题。实际 HTTP 验证九项通过。手机配对及 HID 粘贴没有由这些检查推断为通过，仍等待手机侧观察。

## 模型能够识别桥离线

主页与会话状态改为“ESP32 桥未连接”。已有会话可以继续交谈；每轮模型请求都带可信的桥连接、蓝牙连接和输入测试状态。聊天模式只读取状态，不执行手机操作。新会话仍保留先连接的入口要求。

模型等待期间掉线、执行前掉线和执行中掉线分别处理。未发送的输入返回 `DEVICE_BRIDGE_UNAVAILABLE`；蓝牙断开及未通过输入测试有独立原因。如果输入已经提交后才失联，保留结果未知，不宣称输入从未发出。离线失败不会自动重发。

用现有 DeepSeek 测试凭据做了一次真实模型请求，传入模拟离线状态，模型正确回答当前桥断开、不能发送按键；没有硬件调用。[真实模型结果](bridge-state-model-verification.json)

## 长文本复制与粘贴

工具 `phone_prepare_clipboard` 准备本地文本并暂停任务。用户回到 Harness 点击“复制并继续”，浏览器真实 `writeText` 成功后生成绑定当前会话和目标的回执，再记录本地事件并开始新的任务轮次。该轮必须重新观察、返回目标 App 并确认输入框，再通过支持的键盘操作粘贴。不会从复制回调直接发 HID，也不靠固定延时假定焦点已正确。

待复制、复制失败、取消或归属不匹配时，计划及实际报告中的粘贴快捷键被拒绝。复制回执不证明系统剪贴板没有被其他 App 修改，也不证明目标应用已经输入成功；结果仍需截图确认。

复制成功但本地记录失败时有“重试继续”，仅重试记录与继续，不再次写系统剪贴板。同会话关闭再打开不会丢失待完成写入/记录的恢复状态；切换会话或目标使旧请求失效。继续操作明确恢复 task 模式，并保留用户未发送的草稿。

[WebKit](https://webkit.org/blog/10855/async-clipboard-api/) 要求写入发生于用户手势中，[W3C](https://www.w3.org/TR/clipboard-apis/) 要求文档获得焦点。后台录屏回调不能提供此权限。因此实现需要一次前台点击，没有宣称后台自动复制。

在实际浏览器 DOM 中使用模拟剪贴板验证：拒绝写入时零继续；写入成功但保存失败可重试；重试仅增加保存次数，不增加写入次数。[浏览器结果](clipboard-evidence/browser-result.json)。测试没有覆盖电脑系统剪贴板，也没有发手机输入。
