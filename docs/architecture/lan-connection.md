# 手机与 ESP32 的局域网连接

网站负责对话、录屏和调用模型；ESP32 负责把操作发送到手机。手机与 ESP32 的控制数据应在局域网内直接传输，网站服务器不转发这些指令。

首次使用时，在烧录页面查看设备的 Wi-Fi 名称和密码。手机连接这个 Wi-Fi，打开 `http://192.168.4.1`，填写家里的 Wi-Fi 名称和密码。之后切回家里的 Wi-Fi，再回到 Harness。设备设置页和电脑烧录页都可以提供返回链接，自动带入设备地址和连接码；连接码放在链接的 `#` 后，不进入网站请求。

这是目标操作流程，**当前 iOS 27.0.1 的直接 HTTP 路径尚不能作为已验收功能发布**。2026-10-18 的真机测试显示：手机直接打开局域网 HTTP 地址可以读到测试 JSON；但是从 `https://igent.cc` 发起 HTTP GET、带 `targetAddressSpace: 'local'` 的 GET、JSON POST 和 WebSocket 都立即失败，局域网测试服务器没有收到这四次请求。证据见 [真机连接测试](../research/ios-lan-probe20261018.json)。不能把“固件支持 HTTP”当成“Safari 网页已经能访问固件”。

## 本地连接窗口

测试页面可以由用户点击打开一个设备局域网 HTTP 窗口。这个窗口与设备同源，自行发起 HTTP 请求，再通过浏览器的 `postMessage` 将结果返回 HTTPS Harness 窗口。代码只接受预期的窗口、来源和随机测试标识。

这条路径没有云端转发，也不需要证书安装。真机已经通过连接窗口前台、Harness 后台时的 GET／POST 测试。当前候选代码要求连接窗口隐藏、Harness 可见时成功完成一次请求，才显示连接就绪；随后五轮 GET／POST 真机测试通过，其中包含录屏期间两个页面都隐藏的请求。五轮网络请求覆盖约 21 秒；不能由此宣称无限后台运行或已经验证实体 ESP32 的手机操作。

## 如果需要直接 HTTPS

另一条可行的架构是给每块 ESP32 配置浏览器信任的公开证书：设备生成自己的私钥和证书请求，签发服务完成 DNS-01 验证，设备域名解析到该设备的局域网 IP。证书签发服务只处理设备证书、DNS 和续期，手机操作仍直接发往局域网设备，不经过网站服务器。

这需要实现每设备证书签发与续期、IP 变化后的 DNS 更新，并验证常见路由器的 DNS 行为。不会把一份通用证书私钥写入所有开发板。它目前只是备选架构，尚未实现或验收。

## 当前代码边界

- ESP32 HTTP 候选实现保留原有 `/v1` 配对、手机匹配、独占控制、连续操作、结果查询和停止接口，不再为普通配网生成私人 CA。
- 网页只允许 RFC1918 私有 IPv4 地址或 `.local` 的 HTTP 地址；HTTPS 地址仍能兼容。普通设备地址不接受公网 HTTP、用户名密码、附加路径或查询参数。
- HTTP 请求携带 `targetAddressSpace: 'local'`。此参数不能使尚不支持该能力的 Safari 自动放行。
- `publicKeyFingerprint` 在 HTTP 候选实现中仅为兼容旧协议而保留的稳定设备标识，不证明 TLS、链路加密或证书身份。实际控制仍需连接码、客户端令牌和手机输入验证。
- 局域网测试页面只读取身份、发送无操作的探测内容和检查 WebSocket 回显，不发送键盘或鼠标输入。

### 连接窗口的生命周期

当前本地连接实现为每次连接生成独立的窗口名称和随机标识。不能重复使用固定名称后仅修改 URL 的 `#`：浏览器可能只更新片段而不重新加载旧窗口，旧窗口仍持有上一次连接的标识，导致新页面一直等不到响应。

断开时应先结束当前连接的等待请求，再关闭自己创建的窗口；页面刷新后创建新的连接窗口，不接管旧页面遗留的窗口。每次消息仍须同时核对窗口对象、准确来源、连接标识和请求标识。关闭连接窗口导致正在执行的操作失去回执时，应保留“结果未知”，不能自动重发操作。
