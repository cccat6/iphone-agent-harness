# 提示词与 Skill

## 1. 从参考实现得到的决定

- Codex：基础指令、环境和工具边界分开；长期任务需要上下文预算、工具结果与恢复状态。
- DeepSeek Harness：借鉴动态上下文与稳定系统前缀的分离、Skill 目录与正文的分离；不采用其插件注册和装配框架。
- pi：借鉴小内核、事件流、用户 steering 与工具循环；会话历史与发给模型的投影分开，prompt 组合用普通固定代码。
- OpenCode：按当前工具生成指导；流式输出和执行事件有各自顺序；有输出后的重试不能当作一次全新未执行请求。
- DeepAgents：按需披露 Skill；摘要中间件独立；当前代码已将旧的通用 base prompt 标为弃用，不能拿该常量当现行唯一系统提示词。
- UI-TARS／Anthropic Computer Use：动作空间、坐标、图像历史、错误与终止状态明确。参考其公开实现，不把桌面专用动作或要求输出详细 Thought 的模板原样搬过来。

## 2. 我们的 prompt 组装

稳定部分：产品角色、证据规则、可执行动作、批量执行语义、能力边界、数据规则、完成／失败规则。原创草案见 `prompts/system.md`。

每轮动态上下文：目标 ID、board bootId、方向版本、当前帧及其时刻、实际能力、当前按键释放状态、剩余预算、设备连接、已加载 Skill 版本、最近错误。屏幕文字与 Skill 资源不冒充系统消息。

模型适配层只加必要的 schema、坐标或工具消息格式；不把一种模型的私有系统提示词当成所有模型通用方案。prompt 版本、工具 schema 版本、Skill hash 和模型配置摘要都写入会话，以便复现。

## 3. Skill 包结构

```text
skills/<id>/
  manifest.json          版本、触发描述、所需能力、文件 hash、入口
  SKILL.md               操作方法、观察要求、成功条件和停止条件
  recipes/*.json         可选的声明式动作模板，不是任意 JS
  references/*.md        按需说明
  fixtures/              脱敏测试画面与预期结果
```

入口遵循 name/description 的渐进披露思路；浏览器不会直接执行桌面 Skill 的 shell、Python 或任意脚本。核心执行能力固定，Skill 内容只能指导和组合已有操作；新增能力修改项目代码，不通过 Skill 安装新执行器。

接口：`list → select → load(id,version) → propose plan → validate → execute → verify`。系统常驻目录只含简短 metadata，匹配后读取完整正文。正文版本与文件哈希锁定到当前 run；更新不会在一个按住的手势中替换实现。

本地只维护用户选择的 Skill 清单和对应内容缓存，允许启用／停用／移除。不同来源的同名 Skill 不静默覆盖；以来源和 ID 区分，用户明确选择启用项。能力不满足的 Skill 不暴露为可用，不能让模型临时发明未实现工具。

## 4. 验证码作为可更新的专业 Skill

按用户确定的产品方向，允许在用户授权的任务中通过可见界面自动处理验证码。没有“所有验证码都默认转人工”的产品限制。框架不宣称任何类型都能成功，实际取决于视觉模型、画面、交互方式和服务端接受结果。

统一 `challenge` 分类与结果，不把某厂商的流程写进核心。

| 家族 | 需要的能力 | 处理形态 |
|---|---|---|
| 勾选／确认 | 新截图、点按 | 点按后重新观察是否出现下一层 |
| 文本／算式 | 图片、可用字符输入 | 识别、输入、提交、观察接受结果 |
| 图片选择 | 多区域视觉、连续点按、截图 | 选择有限候选；动态换图后重新观察 |
| 滑块／拼图 | 带时间轨迹的拖动、连续截图 | 依据画面规划路径，释放后确认 |
| 旋转／排序 | 点按或单指拖动 | 按类型加载 recipe，不需要多指旋转手势 |
| 动态／时序 | 有实际时间标记的多帧 | 先验证采样密度足够，再规划动作 |

核心只提供 `challenge.detect` 的分类资料与路由元数据；V1 可由当前视觉模型结合 Skill 完成分类，不假装存在已经训练好的本地分类器。各家族的正文、示例和校验条件独立更新。

结果约定：`solved / failed / changed / insufficient_evidence / unsupported / needs_user`；记录 family、Skill 版本、尝试次数、所依据 frameId 和结果截图。一次点击被设备接收不等于验证码被接受；必须看到挑战消失、明确成功提示或任务页面继续。挑战刷新后废弃旧坐标。

Skill 可以提出一次多个确定操作和中途取图，但不能在图片会重排时盲目执行剩余旧坐标。每次尝试有时限和次数预算；失败反馈用于选择下一次观察，不无限刷新重试。短信／邮件一次性口令需要用户提供或未来另行授权的数据源，不能靠截图 Skill 声称能取得。

不需要把第三方账号凭据、Wi-Fi 密码或 API Key 放进验证码 Skill。当前设计使用用户可见的界面操作；不依赖私有反机器人接口、伪造平台签名或读取其他 App 内存。

## 5. 更新机制

- 站点一起托管 `skills/catalog.json` 和各 Skill 的包／正文文件。目录列出名称、描述、来源、版本、内容地址、hash 与所需能力。
- 用户点击添加时，本地记录来源、ID、版本、启用状态、更新策略，并把正文和参考文件存入 IndexedDB；不只是保存一个会失效的远程链接。
- 用户打开 Skill 页、手动检查或允许自动更新时，只检查已安装项的版本与 hash。未安装的社区 Skill 不自动进入模型上下文。
- 更新先下载到 staging、检查结构／大小／路径／hash，再切换活动版本；失败保持旧版本。运行中的任务固定其 Skill 版本，在任务安全边界以后应用新版本。
- 远程来源暂时不可用或内容删除时，保留本地已安装版本并标记更新失败；移除只影响该用户的本地安装，不删除社区共享内容。
- 发起模型请求时，按任务需要读取本地已启用 Skill 的目录和正文，随本次上下文提交给用户配置的 AI 后端；更新服务不接收用户任务、截图或会话。
- 同源静态文件直接读取；其他共享来源需要允许浏览器跨域读取，否则可以下载包后离线导入。
- 包不能引用上级目录或混入可执行脚本；文本和示例中的指令不会扩大运行时权限。
- 普通新正文或 recipe 更新无需重新刷 ESP32；新 HID 能力需要固件与能力字典一起升级。
- 官方发布可增加签名以验证发布者，但哈希只证明内容一致，不能单独证明可信发布者。

## 6. 用户上传与分享

“本地使用”和“公开发布”分开。用户可以在本地编辑／导入一个 Skill，选择导出包或分享自己托管的内容地址；其他用户添加该地址后在各自手机缓存内容。

第一版共享流程：导出 Skill 包 → 在 GitHub 提交给公共技能目录，或自行托管包 → 发布 catalog 条目／共享链接 → 其他用户添加。官方目录更新只是静态资源发布，不需要保存使用者的安装列表。

若需要站内直接点击“上传并公开分享”，纯静态托管不能接收和持久化上传，须增加一个独立的发布服务，接收用户主动公开的 Skill 文件和基本作者信息，生成静态内容和目录。它只负责共享内容，不负责 Harness 的会话、截图、密钥或运行。

V1 不建设通用插件市场、依赖解析、动态代码加载或复杂 provider 生命周期。上传服务未实现时，页面提供导出／共享链接或仓库提交入口，不把不可用上传按钮当作功能已完成。

## 7. 第一批内置 Skill

`phone-navigation`、`text-entry`、`list-scroll`、`drag-and-drop`、`temporal-observation`、`challenge-router`。验证码家族按验证进度逐个增加，不把空目录登记成已支持。

本轮提供路由 Skill 的设计模板 `apps/web/skills/challenge-router/`；其中没有一个已运行的验证码求解器。开发版 manifest 已记录该模板的真实文件 hash；正式发布前须完成家族实现和夹具验收，不能仅凭该清单宣称功能可用。
